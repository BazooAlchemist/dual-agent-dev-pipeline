# Development Pipeline

将已明确的开发目标推进到约定的交付证据。按真实改动选择环节，不要求固定十二步、全仓库阅读或每次外部审查。

## 执行边界

- 复用用户目标、项目规则和已有判断。先确认目标目录、现有改动以及什么结果算完成；只补会改变实施路线的未知信息。
- 已授权实现或修复包含必要的本地修改、适当检查、修复本次引起的问题并复验。到用户要求的运行或交付层才完成，不在首版代码后无故停下。
- 发布、生产操作、破坏性操作和实质扩围需要对应授权；已有授权不重复询问。暂停受阻动作，继续独立的已授权工作。

## 按未决问题选环节

| 实际问题 | 采用的动作 |
| --- | --- |
| 产品目标或方案存在影响结果的歧义 | 有针对性地澄清或设计；不对明确的小修改强制 brainstorming |
| 服务边界、数据迁移或难逆决策 | 阅读对应架构/数据资料，比较必要方案和回滚条件 |
| 当前工作区存在冲突或需独立试验 | 使用隔离目录或 worktree；无需隔离时直接修改 |
| 新增或修复可观察行为 | 用能捕获该行为的测试验证；测试先行是否有帮助由具体任务判断 |
| 文案、低影响配置或格式调整 | 使用适当的解析、差异或呈现检查；不追加与改动无关的测试 |
| 权限、外部输入、数据完整性等具体风险 | 选择相关安全检查、故障路径或运行证据；不默认全量扫描 |
| 用户要求互审，或项目明确要求独立审查 | 使用实际可用且获授权的审查工具；只有执行了才报告完成 |
| 用户要求发布 | 验证预期文件、版本和目标远端，提交推送后核对远端提交/标签 |
| 暂停或交接确有连续性需求 | 更新现有进度记录，保留下一步和不可重复动作 |

技能与工具以当前可用能力为准，不假定某套插件已安装。需要 Codex 与外部 CLI 的双代理审查且有授权时读取 `dual-agent-code-audit`；没有该能力则报告具体缺口，不模拟身份。模型选择遵从用户和宿主约束。

## 验证与收口

- 每项检查对应真实失败层或验收问题；通过后只因新增受影响改动或新证据复验。
- 不以删测、放宽断言、跳过验证或降低验收标准换取通过。任务确需更新测试、schema 或基准时，说明行为变化并检查新的标准是否仍验证用户结果。
- 不把测试数量、扫描通过或审查同意当成运行证明。明确实际完成层、剩余阻塞和恢复条件。
- 重复失败不原样重跑；长任务、反复排障或成本复盘按需使用 `longtask`，遵守既定预算。
- 仅整理本次工作，保留无关变更和恢复点；不自动清理其他分支或 worktree。

本版取代原固定流程与失效的 AGENTS.md v1.1 引用；不存在由本技能隐式授权的双代理、推送或生产操作。

## Optional legacy bridge integration

Only when the project explicitly adopts this repository's dual-agent bridge, use `schema/audit-request.schema.json` and `schema/audit-response.schema.json` with `core/04-dual-agent-audit.md`. This does not activate the bridge or impose the legacy workflow on ordinary Astra tasks.
